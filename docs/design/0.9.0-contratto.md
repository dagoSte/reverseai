## 2. Esito di un tentativo fisico

Proprietario: lane adattatori. Un tentativo è un avvio della CLI agente; più richieste HTTP interne alla stessa CLI non sono altre api Hive. Una chiamata logica ha nome stabile, ad esempio `m01-build`, e uno o due tentativi: primario ed eventuale locale. Il controllo rete che avvia una CLI è un tentativo distinto, di tipo `network_probe`.

Ogni adattatore restituisce `BeeResult`, dizionario JSON con `schema="hive.bee-result/1"`, campi `ok: bool`, `outcome: str`, `output: object|null`, `error: str|null`, `seconds: number`, `refused: bool`, `code: str|null`, `provenance: object`. Campi già presenti come `turns`, `cost_usd`, `warning` restano opzionali. `ok` è vero solo con `outcome="ok"` e JSON valido per lo schema richiesto; `refused` è vero solo con `outcome="provider_refusal"`. La queen consuma `outcome`, mantenendo gli alias per i chiamanti precedenti. Oggi Claude esige solo un oggetto mentre Codex valida il proprio schema (`hive/bees.py:170`; `hive/codex_bees.py:169`): la nuova validazione deve essere comune.

| `outcome` | Segnale e trattamento |
|---|---|
| `ok` | Turno concluso, nessun errore terminale e schema del ruolo verificato. |
| `provider_refusal` | Segnale strutturato di rifiuto oppure prosa esplicita del modello/diagnostica del fornitore, anche locale. Non cercare nel testo di strumenti, nel campione o nel codice generato. |
| `timeout` | Deadline del processo agente scaduta; nessuna risposta tardiva utilizzabile. |
| `rate_limit` | Codice di quota/429 del fornitore o messaggio terminale equivalente, distinto dal rifiuto. |
| `invalid_schema` | JSON mancante/malformato, campi o valori non conformi, oppure turno senza completamento utilizzabile. |
| `context_limit` | Segnale esplicito di limite del contesto/token, non dedotto dalla sola lunghezza del file. |
| `failure` | Guasto di processo, rete, autenticazione, configurazione o controllo di isolamento; `code` distingue la causa. |
| `not_started` | La queen ha negato la prenotazione per budget/stop, o manca un prerequisito locale. Nessuna risposta di modello inventata. |

Ordine: classificare prima il segnale terminale strutturato; poi la diagnostica terminale completa; poi prosa dell'assistente priva di output valido; infine JSON/schema o guasto generico. Non promuovere una risposta con errore terminale a `ok` solo perché contiene un oggetto. Segnali strutturati contraddittori producono `failure`, `code="inconsistent_terminal"`. Timeout del processo ha precedenza sui suoi output parziali. Non usare un'altra inferenza come classificatore.

Riconoscere almeno le forme esistenti (`hive/bees.py:22`) e rifiuti diretti come `I cannot help with reverse engineering this software.` / `I can't assist with that request.`; escludere frasi citate nei risultati degli strumenti e negazioni come `no usage policy violation`. Prosa dubbia resta errore, con motivo conservato; non promettere completezza semantica per ogni lingua. Classificare prima di ridurre il testo, come già fa Codex (`hive/codex_bees.py:161`). Limite dell'estratto nel risultato: 300 caratteri; diagnostica nativa separata, con limiti espliciti e indicatore di troncamento. Mai copiare credenziali o header di autenticazione nei rapporti.

Il divieto rete Codex rimane `failure`, `code="network_isolation"`, non attiva il fallback. Esiti di una sonda sono registrati come sonde; non sostituiscono l'esito del lavoro. `result.json`, `REPORT.md` e `hive.log` espongono esito, ruolo, nome, tentativi, provenienza, storico e rifiuti ancora irrisolti. I nomi dei verdetti finali restano quelli attuali: `accepted`, `accepted without behaviour proof`, `not accepted`, `not started` (`hive/queen.py:1057`; `hive/queen.py:1010`).

## 3. Scelta esplicita del percorso locale

Proprietari: adattatori per configurazione/selezione; queen per attivazione, budget e persistenza. Restano i flag iniziali `--model-server`, `--model`, `--codex-model`, `--bee-policy`. La radice `http://127.0.0.1:11434` va a Claude come `ANTHROPIC_BASE_URL`; **solo Codex** aggiunge `/v1` per Responses (`hive/selfhost.py:59`; `hive/selfhost.py:85`). Una radice già terminante in `/v1` è errore di configurazione in 0.9.0, così non viene generato `/v1/v1`. URL con credenziali, query o fragment restano vietati (`hive/selfhost.py:42`).

Nuovi flag, registrati da `selfhost.add_arguments`:

| Flag | Regola |
|---|---|
| `--fallback-model-server URL` | Configura e autorizza il fallback al server indicato; assente significa nessun fallback. |
| `--fallback-model NAME` | Modello locale delle api con client Claude. |
| `--fallback-codex-model NAME` | Modello locale delle api con client Codex. |
| `--fallback-scope run\|role\|bee` | Obbligatorio con il server; definisce l'estensione del consenso. |
| `--fallback-role ROLE` | Ripetibile; obbligatorio solo con scope `role`. Valori `planner`, `worker`, `repair`, `councillor`, `tester`. |
| `--fallback-bee NAME` | Ripetibile; obbligatorio solo con scope `bee`, corrispondenza esatta del nome logico, senza glob. |

Le liste di selezione estranee allo scope sono errori. Il server fallback deve essere loopback; `--model-server-remote` resta riferito al server primario e non estende il consenso al fallback remoto. Nessun download, avvio di server o scelta automatica del modello. Entrambi i nomi modello sono obbligatori se la policy può usare entrambi i client. Un server solo Chat Completions non soddisfa Responses/Messages; l'incompatibilità torna `failure`, senza ritorno nascosto al cloud.

La queen controlla la presenza delle sole CLI effettivamente usate, anche nei target di fallback, senza imporre login cloud a una configurazione interamente self-hosted; resta l'ambiente allowlist della base (`hive/selfhost.py:55`). La base controlla Claude anche per la policy Codex (`hive/queen.py:1129`): quel controllo va reso dipendente dalla policy. Una URL loopback non prova che il server non inoltri altrove: il pilot deve identificare modello/digest e verificare la configurazione del server prima di dichiarare elaborazione locale o assenza di consumo cloud.

Senza flag: comportamento di arresto. Con consenso: il primo `provider_refusal` di una chiamata selezionata consente **un solo tentativo locale aggiuntivo**, purché la destinazione differisca dal primario e resti budget. Un altro rifiuto locale chiude la chiamata; timeout, rate limit, schema, contesto e isolamento non attivano quel percorso. Vietati loop tra provider, tentativi non contabilizzati e riscrittura automatica del prompt per eludere il rifiuto.

Scope `run`: dopo il primo rifiuto selezionato la destinazione locale si applica a tutte le nuove api della corsa. Scope `role`: l'attivazione riguarda il solo ruolo rifiutato incluso nella lista; altri ruoli della lista si attivano solo dopo il proprio rifiuto. Scope `bee`: riguarda solo quel nome. Api già attive terminano sulla destinazione iniziale. Le attivazioni sono persistenti e non sono mutazioni dell'oggetto di configurazione condiviso tra thread.

Esempio di consenso per il planner, con server/modello già predisposti dall'operatore:

```sh
python3 -m hive run --inputs /approved --file program --out run-dir \
  --fallback-model-server http://127.0.0.1:11434 \
  --fallback-model local-model --fallback-scope role --fallback-role planner
```

Con questa policy un rifiuto di `planner-g0001` può produrre la sequenza `provider_refusal → ok`; il primario e il locale consumano ciascuno una posizione nel budget. Il successivo gruppo planner usa direttamente il locale. L'esempio non autorizza installazioni né avvia una prova in questo incarico.

Ogni tentativo registra `attempt_id`, `logical_id`, `kind`, `role`, `bee`, `client`, `server_kind=cloud|local`, identificatore del server senza segreti, `requested_model`, `observed_model|null`, `model_digest|null`, `context_id`, origine `primary|fallback`, esito e hash dei sorgenti che produce. I valori osservati sconosciuti restano null, non vengono ricavati dal nome del client.

Per modulo e revisione, la queen conserva gli `attempt_id` di tutti gli autori. I seggi di lettura devono avere contesti nuovi, non essere autori e ricevere solo sorgente rinominato, contratto e brief, secondo il council esistente (`hive/queen.py:733`). Registrare separatamente `model_diversity=true|false|null`: `true` richiede identità/digest di modello verificati e differenti tra autore e lettore; `false` indica identità verificata uguale; con identità sconosciute resta null. Due CLI che servono lo stesso modello non provano diversità di modello. L'uso di un solo modello locale consente letture con contesti indipendenti, senza dichiarare diversità di modello; non cambia il requisito che ogni seggio risponda né consente a un autore di approvare il proprio tentativo. La policy `mixed` mantiene l'instradamento dei client corrente (`hive/codex_bees.py:235`).

## 4. Confine adattatori → queen

Le firme nuove sono normative; i tipi qui indicati sono dizionari JSON e callable, senza dipendenza da una nuova libreria.

```python
# hive/bees.py — lane adattatori
class AttemptNotStarted(Exception):
    pass  # code: budget_exhausted | refusal_limit | run_stopped

class AttemptHooks:
    def __call__(self, kind):
        ...  # -> attempt_id: str, oppure AttemptNotStarted
    def finished(self, attempt_id, result):
        ...  # persiste l'esito di ogni processo agente, sonde incluse

def classify_result(*, terminal, assistant_text, diagnostic, output, schema):
    ...  # -> BeeResult senza provenienza, completata dal runner

# ClaudeBees e CodexBees; MixedBees inoltra i due keyword
def __call__(self, role, name, task, folder, *, schema=None, before_start=None):
    ...  # -> BeeResult

# hive/codex_bees.py — nuova factory, build(...) precedente resta disponibile
def build_router(args, claude_runner, **runner_kwargs):
    ...  # -> BeeRouter

# hive/selfhost.py
class BeeRouter:
    def primary(self, role, name):
        ...  # -> runner della policy claude/codex/mixed
    def fallback(self, role, name):
        ...  # -> runner locale, oppure None se la selezione non autorizza la chiamata
    def describe(self, role, name, *, local=False):
        ...  # -> provenienza + probe_key: str|null, probe_required: bool; senza CLI/rete
    def policy(self):
        ...  # -> configurazione normalizzata, immutabile e senza segreti
```

`schema=None` usa lo schema attuale del ruolo; uno schema esplicito sostituisce quello di output, conservando strumenti e role card del ruolo. Entrambe le CLI devono validarlo. `before_start(kind)` è un callback della queen che restituisce un `attempt_id` prenotato e persistito, oppure solleva `AttemptNotStarted` prima dell'avvio. Il runner lo chiama una volta prima di ogni processo agente, comprese le sonde di rete (`kind="bee"` oppure `"network_probe"`); non lo chiama per compilatore e MCP. Con hook assente resta compatibile l'uso isolato degli adattatori, ma il percorso Hive 0.9.0 lo passa sempre. Il risultato conserva l'ID dell'ape; gli esiti delle sonde sono registrati separatamente dalla queen attraverso il medesimo contesto di tentativo. Per completare la registrazione, l'hook espone anche `finished(attempt_id, result)`, chiamato per ogni avvio prenotato, sonde incluse; la queen può ricostruire un avvio interrotto anche se manca questa chiamata.

La queen possiede l'attivazione degli scope e passa al runner primario o fallback il lavoro; gli adattatori non ritentano autonomamente. Una destinazione locale già attiva viene ottenuta con `fallback` e non ricomincia dal cloud. Descrittori della stessa destinazione/client/modello non costituiscono un'alternativa e non ricevono un secondo tentativo identico. Il controllo Codex è rieseguito quando cambiano destinazione, modello o configurazione della sandbox; la cache non attraversa quei cambiamenti. `probe_key` identifica client/target/modello/modalità per il conteggio Q del punto 6; chiavi duplicate contano una sola sonda pendente. Un fallimento della sonda non viene trasformato in consenso a saltarla.

Prima di ogni tentativo la queen crea un'area di lavoro privata dalla stessa baseline. File parziali del tentativo rifiutato/fallito restano nelle sue evidenze, mai nella baseline del tentativo locale. Con `ok`, la queen promuove solo i file del ruolo: planner gerarchico `PLAN.md` facoltativo (i dati vincolanti sono nell'output), worker/repair sorgenti assegnati, `claims.json`, `NOTES.md`, tester gli eventuali file dei casi previsti dal suo schema. Le riparazioni locali ricevono un sorgente; `behaviour-fix-*` può ricevere l'insieme esplicito dei sorgenti dei moduli, come la base (`hive/queen.py:878`), mantenendo compilazione e nuovo council per ogni modulo cambiato. Contratto, brief, mappa e file della queen sono protetti e non vengono copiati indietro. Nessun link simbolico/hard link è accettato. Il council è sola lettura. In caso di interruzione durante la promozione, la revisione precedente non resta valida: gli hash vengono ricontrollati prima del riuso.

Le aree dei tentativi sono fuori dai moduli canonici, sotto `.hive/attempts/`; configurazioni MCP e schemi generati dalla queen rimangono fuori dall'area scrivibile dell'ape. Le evidenze derivano da programmi e possono essere sensibili: limiti di dimensione/troncamento dichiarati; nessuna pubblicazione automatica. La prova `ok` di un runner non equivale all'accettazione di un modulo.

## 5. Ripresa e rifiuti persistenti

Proprietario: lane queen. Stato autorevole `.hive/run.json`, schema `hive.run-state/1`; tentativi append-only `.hive/attempts.jsonl`. La queen è l'unico scrittore, con lock di processo sul workspace, aggiornamenti atomici e verifica di coerenza all'avvio. Un secondo processo sullo stesso `--out` si ferma. Le copie `modules/*/status.json` non sono autorevoli: il precedente uso di `.hive/status` resta (`hive/queen.py:596`).

Lo stato conserva almeno: `run_id`, hash input/mappa, linguaggio, `plan_id`, `contract_sha256`, `interfaces_sha256`, `planning_policy_sha256`, `compiler_policy_sha256`, contatori, limite, stato/causa di arresto, chiamate logiche e tentativi, rifiuti grezzi e irrisolti, attivazioni locali e hash della policy di routing, autori e binding delle letture per revisione di modulo. Gli hash sono SHA-256 sui byte; JSON strutturali usa `json.dumps(sort_keys=True, separators=(",", ":"), ensure_ascii=False, allow_nan=False)` codificato UTF-8.

`plan_id` è l'hash del payload canonico con hash input/mappa/partizione/policy di pianificazione, linguaggio, moduli/skip, hash contratto e interfacce; esclude timestamp, percorsi assoluti, contatori e il campo `plan_id` stesso. La policy include limiti, versione degli schemi e hash della role card planner. L'identità del contratto dipende dai byte reali, non dal nome del modello. La provenienza delle proposte è conservata separatamente e non viene riscritta al cambio di modello.

All'avvio: verificare input, survey e manifest di piano; se il piano congelato è integro, **caricarlo senza chiamare un planner**. La base oggi ripianifica ad ogni run (`hive/queen.py:957`). Input/mappa/linguaggio/policy di pianificazione incompatibili o manifest danneggiato fermano la ripresa con `failure`, `code="resume_mismatch"`: nuovo `--out` per ripianificare, senza sovrascrivere quello precedente. Un vecchio workspace 0.8.0 privo di manifest autorevole è leggibile per diagnosi, ma non viene promosso tacitamente a ripresa verificata.

| Materiale | Riuso o ripartenza |
|---|---|
| Survey e gruppi | Riusare solo con gli stessi hash input/mappa/partizione e policy. |
| Proposte di gruppo prima del congelamento | Riusare output completi validati e file con hash/provenienza registrati; un gruppo interrotto o invalido riparte dalla sua baseline. |
| Piano e contratto congelati | Riusare insieme dopo verifica di tutti i riferimenti; nessuna ricostruzione implicita del contratto. |
| Modulo accettato | Riusare con stessa assegnazione, piano, contratto, sorgente, oggetto e policy compilatore, rapporto worker completo e letture legate agli stessi byte. La base lega già questi artefatti (`hive/queen.py:599`; `hive/queen.py:706`; `hive/queen.py:716`). |
| Oggetto valido ma council incompleto | Riusare compilazione/worker verificati; ripetere la lettura mancante su nuovi contesti. |
| Modulo rifiutato o interrotto | Ripartire dal passo logico incompleto, senza trattare i file del tentativo fallito come accettati. |
| Link/checker/comportamento | Riutilizzare solo risultati legati all'esatto insieme finale di oggetti/input/casi/policy; altrimenti rieseguire. Nessun vecchio binario dopo relink fallito. |

Contatori e storico non si azzerano rilanciando il comando. Un evento `started` privo di termine diventa `interrupted` e resta consumato: la ripresa prenota un nuovo tentativo, non duplica l'ID precedente. Non avviare automaticamente una sessione agente precedente; ogni tentativo usa contesto nuovo come le CLI attuali (`hive/bees.py:140`; `hive/codex_bees.py:142`).

Distinguere `refusals` (storico immutato) da `unresolved_refusals` (ID logici senza sostituzione locale valida). Un primario rifiutato seguito da `ok` locale risolve solo quel lavoro, conservando entrambi i tentativi. Se il locale fallisce o non parte, quel rifiuto resta irrisolto. Il limite di tre riguarda **chiamate logiche irrisolte**, valutato alla fine della catena consentita; sonde rifiutate contano come lavori di sonda irrisolti, senza fallback. Il verdetto impedisce accettazione finché esistono rifiuti irrisolti o altri controlli mancanti; lo storico risolto è riportato senza veto autonomo. Questa è una modifica esplicita al veto su qualunque rifiuto della base (`hive/queen.py:1044`).

Raggiunta la soglia, niente nuove api ordinarie; quelle attive terminano. Per recuperare uno stop per rifiuti serve `--resume-refused` (flag della queen), insieme a selettori/target locali espliciti per i lavori da recuperare: consente solo quei tentativi di recupero fino a scendere sotto soglia, senza cancellare lo storico. Una sonda di isolamento fallita non è recuperata da questo flag. Un precedente stop di budget richiede anche il nuovo limite sufficiente. Omettere la configurazione locale già attiva arresta la ripresa: non riporta il lavoro al cloud di nascosto. Un cambiamento esplicito del target locale viene registrato come revisione della policy, conservando budget e autori.

## 6. Budget e previsione

Proprietario: queen; gli adattatori applicano l'hook prima dei processi. `--max-bees` mantiene default 400, ma in 0.9.0 conta **tutti** gli avvii agenti: primari, fallback, riparazioni, lettori e sonde. La base limita i passaggi attraverso `Queen.bee`, mentre le sonde sono interne al runner (`hive/queen.py:496`; `hive/codex_bees.py:179`). Non è un cap sui token, sugli euro o su ogni richiesta HTTP interna; riportare questa unità anche nell'help.

La prenotazione avviene dopo l'acquisizione del posto di concorrenza e sotto lock: verificare stop e cap, persistere `started`, incrementare il totale, poi avviare. Nessun decremento dopo rifiuto, timeout o crash. Una prenotazione persistita seguita da crash prima dell'avvio è consumata prudenzialmente. `AttemptNotStarted` non crea una risposta modello e non esegue subprocess. Se non resta spazio per una sonda necessaria e il lavoro, fermarsi senza spendere una sonda inutile; capacità della sonda stimata in modo conservativo per client/target/modalità non ancora verificati.

Prima della pianificazione riportare il numero di gruppi G e il minimo G di chiamate planner, oltre alle sonde. Dopo il piano e a ogni ripresa calcolare:

```text
remaining_min = P + U * (1 + L) + V * L + T + Q
recommended_total = spent + remaining_min + max(8, ceil(0.25 * remaining_min))
```

P = planner di gruppo/conflitto ancora necessari; U = moduli che richiedono builder e council; V = moduli compilati che richiedono solo council; L = seggi configurati; T = 1 se occorre generare casi con `--run-original`, altrimenti 0; Q = sonde massime ancora necessarie per le modalità/target previsti. I riusi verificati non compaiono in U/V. La riserva del 25% è **euristica dichiarata**, non garanzia; riparazioni, fallback e conflitti possono superarla. G non è il numero di moduli.

Se `max_bees - spent < remaining_min`, arresto prima di iniziare la fase: `stop_reason="budget_insufficient"` con dati e limite minimo. Se il minimo entra ma la riserva no, avviso e prosecuzione entro il cap esplicitamente impostato. Se il cap viene raggiunto durante la fase, `not_started`, `code="budget_exhausted"`, checkpoint e verdetto incompleto; niente perdita dei moduli verificati. Mai aumentare il cap da codice. Alla ripresa senza nuovo `--max-bees`, usare il limite salvato; un nuovo valore esplicito non può essere inferiore a `spent` e non azzera il consumo. Uno stop per solo budget si sblocca solo con aumento esplicito sufficiente.

Esempio aritmetico, **non misura di curl**: G=48, M=100, L=3, nessun riuso, tester spento e sonde escluse per semplicità ⇒ minimo iniziale 48+400=448 avvii, già oltre 400. Un singolo planner globale avrebbe nascosto 47 di quegli avvii. Il documento non prescrive un limite universale per curl né una durata locale.

## 7. Fase A → fase B: pianificazione per gruppi

Proprietario: lane pianificazione B. `hive/partition.py` resta congelato: espone `partition(program_map, *, max_functions=128, max_bytes=65536, summary_bytes=8192, incoming_limit=128, string_limit=128, outgoing_limit=128, reference_limit=128)` e `write_side_files(result, folder)` (`hive/partition.py:130`; `hive/partition.py:78`). Un globale `defined` ha `owner_entry` che identifica una funzione assegnata al modulo proprietario della definizione; un globale `external` ha `owner_entry=null` e prove della sua risoluzione esterna, senza definizione generata. Un tipo opaco può attraversare il confine solo per puntatore/riferimento; conflitti di layout non si risolvono inventando dimensioni.
